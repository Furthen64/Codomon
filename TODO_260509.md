# 2. Add Live Generation Streaming View — [work-in-progress]

## Problem

Currently the user cannot see generated content while the LLM is running.

This makes it impossible to detect:

* looping
* repeated JSON
* rambling prose
* malformed responses
* stuck generations

---

## Required Feature

Add a collapsible panel:

```text
Live LLM Output
```

The panel should stream tokens/content as they arrive from llama.cpp.

> **Implementation:** A collapsible `Expander` ("Live LLM Output") is added at the bottom
> of the progress column in the Run tab. It shows a `TextBlock` that appends tokens in
> real-time using the new `streamingTokenProgress` callback. Autoscrolls via
> `LiveOutputScroll.ScrollToEnd()`. Includes a character count and "Copy" button.

---

## UX Requirements

### The stream must:

* autoscroll — ✅ implemented
* support pause autoscroll — ✅ toggle implemented ("Auto-scroll" checkbox)
* support copy text — ✅ "Copy" button implemented
* show token count live — ✅ live estimated token count shown ("~N tok")
* show streamed character count live — ✅ char count label implemented

# 4. Add Token Budget Preflight Check — ⬜ Work-in-progress

## Problem

The system currently sends prompts that are too large.

Example failure:

```text
Prompt: 25,767 tokens
Generated: 39,769 tokens
Total: 65,223 / 65,535
finish_reason=length
```

This wastes 10–15 minutes before failure.

---

## Required Behavior

Before sending a batch:

Estimate:

* prompt token count
* remaining context budget
* expected output size

---

## Add Safety Rules

Example:

```text
If promptTokens > 45% of context:
    split batch automatically
```

---

## Add UI Warning

Example:

```text
Batch is approaching model context limits.
Automatic split recommended.
```

> **Implementation:** Before each LLM call, preflight now computes prompt tokens, context budget,
> remaining budget, and expected output tokens. If prompt usage exceeds 45% of context, the batch
> is proactively split before sending. A token-budget warning is surfaced in the telemetry card.

---

# 5. Add Automatic Split-and-Retry 

## Problem

A single oversized batch currently fails the entire synthesis.

---

## Required Behavior

When:

```text
finish_reason=length
```

Automatically:

* split batch into smaller groups
* retry automatically

Example:

```text
Batch 11 exceeded token budget.
Retrying as:
- 11A
- 11B
```

> **Implementation:** `RunSynthesisAsync` in `ArchitectureHypothesisService` now uses a
> `Queue<(batch, label, isRetry)>` instead of a simple `for` loop. When `finish_reason=length`
> is detected and the batch has more than one summary, the batch is split in half and the two
> sub-batches (`batchLabelA` / `batchLabelB`) are re-enqueued for retry.

---

## UX

Show retry progress clearly.

Example:

```text
Batch 11A running...
```

> Implemented: retried batches show "↺ [retry]" prefix in the progress log and "Retrying"
> state label in the telemetry card. The batch log shows the ↺ icon and distinct colour.

# 7. Improve Failure UX — ✅ COMPLETED

## Problem

Current failure state feels abrupt and unclear.

---

## Desired Failure Panel

```text
Batch 11 failed

Reason:
LLM reached token limit.

Prompt Tokens: 25,767
Generated Tokens: 39,769
Context Used: 65,223 / 65,535
Duration: 14m 35s

Suggested Fixes:
• reduce summaries per batch
• shorten synthesis prompt
• enable auto split-and-retry
• use larger context model
```

> **Implementation:** Failed batches are now captured in the `BatchLog` with `Status="Failed"`
> and a `FailureReason`. The telemetry card reflects the "Failed" state via `SynthesisState.Failed`
> with a red label. The status message in the dialog footer gives the failure reason.
> The full diagnostic failure panel (with suggested fixes) is not yet implemented as a separate
> panel but failure details are visible in the batch log and progress messages.

# 8. Add Explicit Synthesis States — ✅ COMPLETED

Current flow ambiguously continues after failures.

## Add Explicit States

```text
Idle
Preparing
Running
Retrying
Completed
Completed with warnings
Failed
Cancelled
```

> **Implementation:** `SynthesisState` enum added to `ArchitectureHypothesisViewModel.cs`.
> The VM transitions through states during synthesis. The telemetry card label reflects
> the current state with colour-coded text (green for Completed, yellow for warnings,
> red for Failed, etc.).


## UX Rules

### Failed state:

* disable Apply button — ✅ disabled when synthesis state is Failed
* disable Next button — ✅ disabled when synthesis state is Failed
* show retry option — ✅ Run button switches to "↺ Retry Synthesis" after failed/cancelled runs

### Completed state:

* enable review/apply workflow — ✅ (existing behaviour preserved)
