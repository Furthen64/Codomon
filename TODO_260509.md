# Codomon — Architecture Hypothesis UX/UI Improvements

## Goal

Improve the Architecture Hypothesis synthesis experience so the user can:

- understand what the system is doing
- estimate remaining time
- detect stalled/rambling LLM generations
- recover gracefully from token-limit failures
- trust the synthesis process

The current experience feels opaque during long LLM calls.

---

# 1. Add Real Run Telemetry Panel — ✅ COMPLETED

## Problem

The user currently cannot tell:

- whether the LLM is progressing
- whether the model is looping/rambling
- whether generation speed dropped
- whether the batch is healthy
- how long remains

---

## Add Top Status Card

Place above the log view.

Example:

```text
Architecture Synthesis Running

Batch 11 / 20
Processed 760 / 1420 summaries
Elapsed: 08m 12s
ETA: ~06m 48s

Prompt Tokens: 25,767
Generated Tokens: 18,442
Generation Speed: 46 tok/sec
Average Batch Time: 42 sec
```

> **Implementation:** A `TelemetryCard` Border is added as a `DockPanel.Dock="Top"` panel
> in the Run tab, visible as soon as synthesis starts. It shows batch number, summary counts,
> elapsed time, ETA, cumulative token counts, and generation speed. All values update live via
> the new `BatchTelemetry` progress callback from the service.

# 4. Add Token Budget Preflight Check — ⬜ Work-in-progress

## Problem

The system currently sends prompts that are too large.

Example failure:

```text
Prompt: 25,767 tokens
Generated: 39,769 tokens
Total: 65,223 / 65,535
finish_reason=length
```

This wastes 10–15 minutes before failure.

---

## Required Behavior

Before sending a batch:

Estimate:

* prompt token count
* remaining context budget
* expected output size

---

## Add Safety Rules

Example:

```text
If promptTokens > 45% of context:
    split batch automatically
```

---

## Add UI Warning

Example:

```text
Batch is approaching model context limits.
Automatic split recommended.
```

> **Implementation:** Before each LLM call, preflight now computes prompt tokens, context budget,
> remaining budget, and expected output tokens. If prompt usage exceeds 45% of context, the batch
> is proactively split before sending. A token-budget warning is surfaced in the telemetry card.

---

# 5. Add Automatic Split-and-Retry — ✅ COMPLETED

## Problem

A single oversized batch currently fails the entire synthesis.

---

## Required Behavior

When:

```text
finish_reason=length
```

Automatically:

* split batch into smaller groups
* retry automatically

Example:

```text
Batch 11 exceeded token budget.
Retrying as:
- 11A
- 11B
```

> **Implementation:** `RunSynthesisAsync` in `ArchitectureHypothesisService` now uses a
> `Queue<(batch, label, isRetry)>` instead of a simple `for` loop. When `finish_reason=length`
> is detected and the batch has more than one summary, the batch is split in half and the two
> sub-batches (`batchLabelA` / `batchLabelB`) are re-enqueued for retry.

---

## UX

Show retry progress clearly.

Example:

```text
Batch 11A running...
```

> Implemented: retried batches show "↺ [retry]" prefix in the progress log and "Retrying"
> state label in the telemetry card. The batch log shows the ↺ icon and distinct colour.

# 12. Add Streaming Support in LLM Client — ✅ COMPLETED

## Important

Current implementation waits for entire response before UI updates.

This creates a frozen-feeling UX.

---

## Required

Use streaming responses from llama.cpp OpenAI-compatible endpoint.

Enable:

```json
"stream": true
```

Then append tokens incrementally to UI.

> **Implementation:** `CallLlmStreamingAsync` in `ArchitectureHypothesisService` now uses
> `HttpCompletionOption.ResponseHeadersRead` + SSE line-by-line reading. Each `data: {...}`
> frame is parsed as a `ChatStreamChunk` and the `delta.content` token is reported via
> `IProgress<string> tokenProgress`. The old blocking `CallLlmAsync` has been replaced.
> Token usage is taken from the server's `usage` field when available, or estimated via
> the 4-chars-per-token heuristic.
