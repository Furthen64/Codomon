# QA Report — Codomon — 2026-05-04

**Scope:** Full codebase review with focus on the Graph, System Map, Roslyn scan,
Summaries, and Architecture/Hypothesis mechanisms.

**Reviewed revision:** current HEAD of `Furthen64/Codomon`

---

## 1. Graph

### 1-A. Node positions are lost on every System Map filter change (High)

`BuildFromSystemMap` and `BuildModuleRelationshipsForSystem` always assign auto-positions
starting at `X=80`, advancing by `autoGap=220` per node.  The legacy
`BuildFromWorkspaceConnections` path correctly reads saved positions from profile data
(`sys.X / sys.Y`), but the System Map path does not.  Any time the user toggles a
relationship-kind filter, `ApplyFilters` → `BuildFromSystemMap` is called, and **all nodes
snap back to a flat horizontal row**, discarding any manual arrangement the user made.

`AutoAlign` is available but must be triggered explicitly by the user; there is no automatic
call to it after `ApplyFilters`, so the default post-filter state is always the raw auto-layout.

**Impact:** Repeated, disruptive UX: every filter toggle resets graph layout.

---

### 1-B. `CodomonGraphAdapter.ToViewModel` — design-time graph loaded in constructor never re-used (Low)

The parameterless `GraphViewModel()` constructor loads a fake demo graph into `Nodes`,
`Connections`, and `_nodeEdges`.  The first call to `Refresh` or `RefreshFromSystemMap` clears
those collections.  Because the constructor also populates `_nodeEdges` for the demo graph,
the internal list is briefly out of sync until the first real refresh.  In normal runtime flow
this is harmless, but it can cause unexpected behaviour in design-time tools or unit tests that
instantiate `GraphViewModel` without immediately calling `Refresh`.

---

### 1-C. `DistributeHorizontally` silently no-ops for fewer than 3 nodes (Low)

The method returns immediately if `nodes.Count < 3`.  The call sites and documentation do note
this, but there is no feedback to the UI, so the user action appears to silently fail.

## 2. System Map

### 2-A. `IdentityKey` is not persisted in SystemMap DTOs (High)

`WorkspaceSerializer.SystemToDto`, `ModuleToDto`, and `CodeNodeToDto` do not include
`IdentityKey` in the serialised DTO.  The matching DTO classes (`SystemDto`, `ModuleDto`,
`CodeNodeDto`) have no `IdentityKey` field.

After a save/load cycle every `IdentityKey` is reset to `string.Empty`.
`FindSystemByKey` / `FindModuleByKey` / `FindCodeNodeByKey` fall back to recomputing the key
from name + kind on each lookup (lazy stamping), so **normal operation continues correctly**.
However, if a system or module is renamed via a `ManualOverride`, the recomputed key after
reload will differ from the key computed before the rename.  A subsequent upsert for the
original name would then create a duplicate instead of merging, silently diverging the map.

---

### 2-B. `UpsertHighValueNode` uses a name-only identity key (Medium)

```csharp
var key = SystemMapIdentity.CreateCodeNodeKey(null, null, null, suggestion.Name);
```

Passing `null` for `fullyQualifiedName`, `projectPath`, and `filePath` causes
`CreateCodeNodeKey` to fall back to a key that is just the normalised simple name
(e.g. `"connectionmanager"`).  Two different classes in different namespaces or assemblies with
the same simple name will be incorrectly merged into a single `CodeNodeModel`.

---

### 2-C. `PlaceCodeNode` silently drops a high-value node when the map has no systems (Medium)

If `map.Systems` is empty (a valid early state before any hypothesis is accepted) the method
logs nothing and returns without placing the node.  The calling code does not check the return
value, so the data is silently lost.

---

### 2-D. `MergeHypothesis` drops modules from a duplicate system's second occurrence (Medium)

When multi-batch synthesis produces the same system name in more than one batch, only the
first batch's `HypothesisSystemModel` is kept; the subsequent one (and all its `Modules`) is
skipped:

```csharp
if (!existingSystemNames.Contains(s.Name ?? string.Empty))
{
    target.Systems.Add(s);
    existingSystemNames.Add(s.Name ?? string.Empty);
}
// else: the system AND its modules list are silently discarded
```

This means modules discovered in a later batch for an already-seen system are never merged.

---

### 2-E. `SystemMapValidator` is not called after workspace load (Low)

The `SystemMapValidator` XML doc says to call it after "loading a workspace", but
`WorkspaceSerializer.LoadAsync` only calls `ManualOverrideService.Apply`.  Inconsistencies
(dangling relationships, duplicate keys) that exist in saved files are never surfaced to the
developer console.

---

### 2-F. `NormalizeKeyPart` regex collapses mixed separator sequences (Low)

The regex `@"[|:]{2,}"` matches any two or more consecutive characters from the set `{|, :}`.
The sequence `|:` (pipe followed by colon) is therefore collapsed to `|`, as is `::`.
While composed keys use `|` and `::` as distinct separators that are never passed back
through `NormalizeKeyPart`, a source name that happens to contain `|` or `:` characters
(e.g. a generic type expression) would produce an unexpectedly collapsed key.

## 3. Roslyn Scan

### 3-A. `ParseFileAsync` silently swallows all non-cancellation exceptions (Medium)

```csharp
catch
{
    // Skip files that can't be parsed (generated, malformed, etc.)
    return null;
}
```

I/O errors (disk full, access denied), out-of-memory conditions, and unexpected Roslyn
failures are all silently discarded with `return null`.  The file is dropped from the scan
results without any trace in the log, making it difficult to diagnose silent coverage gaps.

---

### 3-B. `ExtractCalledClasses` generates false positive connections from framework types (Medium)

The heuristic keeps any identifier beginning with an uppercase letter:

```csharp
if (candidate != null && candidate.Length > 0 && char.IsUpper(candidate[0]))
    names.Add(candidate);
```

This captures `Directory`, `Path`, `File`, `Task`, `Console`, `Guid`, `DateTime`,
`Environment`, etc.  If any of these standard .NET names match a class in the scan, spurious
suggested connections are generated, polluting the `SuggestedConnections` list and potentially
inflating the canvas.

---

### 3-C. `BuildSuggestedConnections` resolves simple names to all matching full names (Medium)

When a simple name like `Logger` matches multiple fully-qualified classes in the scan, a
connection is created to every one of them.  In projects where multiple classes share a name
(common with generated or partial classes), this multiplies connections, many of which will be
wrong.

---

### 3-D. `ListSavedScans` uses filesystem write time, not filename timestamp (Low)

```csharp
.Select(f => (FilePath: f, ScanTime: File.GetLastWriteTimeUtc(f)))
```

The filename already encodes a timestamp (`yyyyMMdd_HHmmss`).  Using write time means that if
a file is copied or its metadata is modified externally, the ordering changes unexpectedly.

---

### 3-E. Scan is sequential — no file-level parallelism (Low / Performance)

Files are parsed one-by-one inside a `foreach` loop.  For large codebases (thousands of `.cs`
files) this is a throughput bottleneck.  The `ParseFileAsync` method is structured for
individual awaiting, making it straightforward to parallelize with `Task.WhenAll` or
`Parallel.ForEachAsync`.

## 4. Summaries (LlmSummaryService)

### 4-A. `CallLlmAsync` does not check `finish_reason=length` (Medium)

`ArchitectureHypothesisService.CallLlmAsync` explicitly checks `finishReason == "length"` and
throws a descriptive error.  The equivalent method in `LlmSummaryService` does not perform
this check, so a truncated summary is silently returned and saved as if it were complete.  The
truncated markdown file then becomes bad input for the hypothesis pass.

---

### 4-B. `LoadPromptTemplateAsync` returns empty string when template is missing (Low)

When the workspace's `summary_prompt.md` does not exist, the method returns `string.Empty`.
The upstream caller (`GenerateAndSaveSummaryAsync`) does not check for an empty template
before sending it to the LLM, resulting in a prompt that contains only the source code with no
instruction.  This is distinct from the hypothesis service, which explicitly throws when the
template is empty.

---

### 4-C. `RelativePathToSafeName` / `SafeNameToRelativePath` are not lossless inverses (Low)

Both path separators (`/`, `\`) and the dot (`.`) are all mapped to `_`.  The reverse
function maps every `_` back to `Path.DirectorySeparatorChar`.  A file at
`src/Foo_Bar/Baz.cs` and one at `src/Foo/Bar_Baz.cs` will produce the same safe name
`src_Foo_Bar_Baz_cs`, and the reconstructed display path for both is identical.  This means
two distinct source files could collide on the file system, with the second silently
overwriting the first summary.

---

### 4-D. `ModuleClassifier.BuildSummaryLookup` expects a flat folder, not the summaries root (Low)

Summaries are stored in timestamped batch subfolders:
`summaries/20250101_120000/MyClass_cs.md`.  `BuildSummaryLookup` enumerates `*.md` files in
the passed folder only (no recursion).  If a caller passes the `summaries/` root it finds
nothing; it must pass the specific batch subfolder path.  This contract is implicit and not
documented.

## 5. Architecture / Hypothesis

### 5-A. `TryRepairTruncatedJson` leaves a mismatched bracket case with original unmodified JSON (Medium)

When a closing bracket does not match the top of the stack (e.g. `}` found where `[` is
expected), the method returns `repaired = json` (the original, unmodified JSON) and `false`.
The caller then skips the repair attempt entirely.  In this scenario the JSON is structurally
invalid but not truncated — the correct action would be to attempt a repair differently or to
throw a more descriptive error instead of passing `json` as `repaired` even when returning
`false`.

---

### 5-B. Duplicate `HttpClient` instances across LLM services (Low / Design)

Both `LlmSummaryService` and `ArchitectureHypothesisService` declare their own static
`HttpClient` with a 30-minute timeout.  While static lifetime avoids socket exhaustion, two
independent instances mean connection pooling is not shared and configuration changes (proxy,
TLS) must be duplicated.  A shared `IHttpClientFactory` or a single shared client would
better reflect the intent.

---

### 5-C. `AppLogger.Append` always marshals to the UI thread (Low / Design)

All logging is dispatched via `Dispatcher.UIThread.Post(…)`.  If logging is called from a
background task during application shutdown (or in a test context without a UI dispatcher),
the post is silently queued but never executed.  Critical error messages (e.g. from the
autosave or LLM call paths) may therefore be lost.

---

## 6. Persistence

### 6-A. `SaveWorkspaceAsAsync` does not update `RecentWorkspacesService` (Low)

`OpenWorkspaceAsync` and `NewWorkspaceAsync` both call
`RecentWorkspacesService.AddOrUpdate(...)`, but `SaveWorkspaceAsAsync` does not.  A workspace
saved to a new location never appears in the recent workspaces list.

---

### 6-B. `WorkspaceSerializer.ReadJsonAsync` throws on empty / null JSON (Low / Robustness)

```csharp
return await JsonSerializer.DeserializeAsync<T>(stream, JsonOptions)
    ?? throw new InvalidOperationException($"Failed to deserialize '{path}': …");
```

A zero-byte file or a file containing only whitespace will throw `JsonException` before the
`??` null-check is reached.  The error message `"Failed to deserialize"` is then lost inside
an inner `JsonException`, making diagnosis harder.  Wrapping in a try/catch with a descriptive
message would improve robustness.
